# Читалка: что делаем в этой версии

Автор: Ника. Дата: 4 сентября 2026. Версия документа: 1.0

## Зачем это нужно

Читалка сейчас знает одного агента. Его адрес лежит в `config.json` одним полем,
автор правки жёстко подписан «Ника», база одна, а выгрузка в ENOT делается руками
через API. Пока агент один — терпимо. Как только появляется второй, ломается всё
сразу: кому уходит кнопка «отправить в работу», кто автор правки, кто отвечает
за документ.

Эта версия закрывает три вещи: несколько агентов с привязкой к документам и
коллекциям, выгрузку в ENOT одной кнопкой и установку из репозитория. Всё
остальное из наших разговоров — в `plan-studio.md`, это следующий продукт.

## Агенты: реестр вместо поля в конфиге

Новый файл `agents.json` в корне Orchestra. В код агенты не попадают — только в
этот файл:

```json
{
  "default": "nika",
  "agents": [
    {
      "id": "nika",
      "name": "Ника",
      "kind": "hermes-webhook",
      "url": "http://127.0.0.1:8644/webhooks/nika-book",
      "secret": "***",
      "enabled": true
    },
    {
      "id": "gera",
      "name": "Гера",
      "kind": "hermes-webhook",
      "url": "http://127.0.0.1:8645/webhooks/gera-book",
      "secret": "***",
      "enabled": false
    }
  ]
}
```

Старые поля `hermes_webhook` и `hermes_secret` продолжают работать: если
`agents.json` нет, читалка собирает из них одного агента и живёт как раньше.
Ничего не сломается на переходе.

## Автоопределение: откуда читалка узнаёт про агентов

Профили Hermes лежат в `~/.hermes/profiles/<имя>/config.yaml`, и там уже есть
всё нужное — порт и секрет webhook:

```yaml
platforms:
  webhook:
    enabled: true
    extra:
      host: 127.0.0.1
      port: 8644
      secret: ...
```

Читалка сканирует эту папку и показывает три состояния:

- **готов** — webhook включён, есть подписка на книгу, связь проверена;
- **найден, связь не настроена** — профиль есть, webhook выключен. Показываем,
  что нужно дописать в конфиг, и на какой порт;
- **не отвечает** — настроен, но шлюз лежит.

Проверено на живой системе: у Ники webhook слушает 127.0.0.1:8644, у Геры ключа
`platforms` в конфиге нет вовсе, порт 8645 свободен. Профилей всего четыре:
nika-redaktor, hefest, mira, tim. Гера сидит в корневом профиле.

Важно: **включить webhook в чужом профиле и перезапустить его шлюз должен
Андрей.** Читалка может показать готовую команду, но выполнить за него не может —
у неё нет доступа к процессу другого агента.

## Адаптеры: чтобы потом не переписывать

Отправка задания уезжает из `hermes_link.py` в папку `agents/`:

```
agents/__init__.py     выбор адаптера по полю kind
agents/hermes.py       webhook + подпись HMAC (то, что уже работает)
agents/cli.py          заготовка: запуск команды в терминале (Codex, OpenCode)
```

У всех один вызов: `send(agent, doc_rel, job) -> (ok, сообщение)`. Новый тип
агента — новый файл в `agents/`, читалку не трогаем. Сейчас реализую только
`hermes`, `cli.py` оставляю каркасом с честной пометкой «не готово», чтобы через
месяц не ломать структуру.

## Привязка: документ, семья версий, коллекция, база

Привязка хранится рядом с замечаниями, в `_notes/<Глава N>.agent.json`:

```json
{ "agent": "gera", "set_by": "Андрей", "at": "2026-09-04T11:20:00" }
```

Файл лежит на уровне **семьи версий**, а не отдельного файла версии. Поэтому
новая версия наследует агента сама — ничего заново привязывать не нужно.

Поиск агента идёт вверх, до первого попадания:

```
файл версии -> семья версий -> папка коллекции -> база -> default из agents.json
```

Коллекции получают привязку так же: `_notes/_collection.agent.json` в папке
коллекции. Новый документ внутри неё подхватывает агента автоматически — ровно
то, что ты просил.

Если не нашлось ничего и `default` пустой — читалка спрашивает один раз при
отправке и запоминает ответ как привязку документа. Больше не спросит.

## Как это выглядит в интерфейсе

В дереве слева у документа и у коллекции появляется меню из трёх точек:

- привязать агента (список включённых из `agents.json`);
- снять привязку (вернуться к наследованию);
- история документа (то, что сейчас за кнопкой со стрелкой).

Привязку показываю в дереве **текстовой меткой** — «Ника», «Гера». Не кружком и
не цветной точкой: цвет ничего не говорит, а имя говорит всё.

Кнопка «отправить в работу» больше ничего не спрашивает: смотрит привязку и
отправляет. В подтверждении перед отправкой пишем, кому именно уходит.

## Автор правки

`notes.add_edit` жёстко ставит `author='Ника'`, у `nika.py mark` параметра автора
нет. Значит правки Геры окажутся в истории моими.

Чиню не подписью от агента, а подстановкой: `mark` и `newver` получают
`--author`, а читалка при создании задания пишет автора в файл задания из
привязки. Агент ничего не указывает — поле подставляется само. Смысл в том, что
привязку ты можешь сменить, а история должна остаться правдивой: через месяц из
«сейчас привязан Гера» не понять, кто правил версию 1.1.

## Синхронизация с ENOT

Проверила базу: **кода синхронизации нет**. Ни в читалке, ни отдельным скриптом.
Есть следы разового экспорта из ENOT в файлы от 2 сентября — в каждом
`_index.md` и в файлах версий лежит front-matter:

```yaml
yonote_id: 4d90066c-5877-4d35-a8c4-07b75a29cb47
collection_id: 151db55a-b27a-41d7-8a59-8b842bd699d2
parent_id: ...
status: synced
synced_at: 2026-09-02
synced_hash: d93cb314d925c275
```

Заготовка под синхронизацию, которую никто не дописал. Сейчас в базе 12 файлов
`synced` и 5 `draft`, то есть расхождение уже есть.

**Поток делаю в одну сторону: файлы -> ENOT.** Причина простая. Версии у нас
неизменяемы, а документ в ENOT правится в браузере в любой момент. Двусторонний
автосинк на таких правилах даёт конфликты, которых не разрулить без ручного
разбора. Файлы — источник правды, ENOT — витрина.

Что делаю:

`sync/yonote.py` — отдельный модуль, `YONOTE_API_KEY` берётся из окружения или
из `config.json`:

- `documents.update` по `yonote_id`, если он заполнен;
- `documents.create` с `collectionId` и `parentDocumentId`, если пустой —
  и `yonote_id` дописывается в front-matter;
- после записи обязательная проверка через `documents.info`;
- `synced_hash` и `synced_at` обновляются по факту успеха.

В интерфейсе: кнопка «отправить в ENOT» на странице документа и страница
«что расходится» — обход базы со сравнением хэша, три состояния (совпадает,
файл новее, в ENOT нет вовсе).

Две ловушки, которые уже известны и учтены в коде:

- Yonote API съедает `**жирный**`, `*курсив*` и `[текст](url)`. Метки сносок
  `[N]` и прямые URL сохраняет. Поэтому выгружаем простым форматом, ссылку пишем
  прямым видимым `https://...`.
- Через твой VPN TLS до `app.yonote.ru` рвётся. Нужны ретраи с паузой, иначе
  выгрузка будет падать на ровном месте. Ошибку показываем честно, без
  «попробуйте позже».

## Установка из репозитория

Чтобы не собирать руками на каждой машине:

```
install.sh / install.ps1     проверка Python, создание config.json из образца,
                             поиск базы, поиск профилей Hermes, ярлык запуска
agents.example.json          образец реестра
config.example.json          уже есть
.gitignore                   config.json, agents.json, __pycache__ — уже есть
README.md                    установка в три строки
```

Внешних библиотек не добавляю. Читалка работает на чистой стандартной
библиотеке Python, и это её сильная сторона: ставится где угодно, не ломается от
обновлений.

## Что беру попутно, потому что дёшево

Четыре вещи, каждая — меньше получаса, а пользы много:

**Поиск по базе.** 780 файлов и ни одного способа найти абзац. Обычный текстовый
поиск с подсветкой и переходом к блоку. Без нейросети — она пойдёт в студию.

**Сравнение версий в браузере.** `diff` уже написан в `nika.py`, но живёт только
в командной строке, и ты его не видишь. Вывести в HTML — кнопка «что изменилось
с 1.0».

**Проверка сносок.** У нас формат `[N]` плюс блок «Источники к главе N».
Механическая сверка: метка без пункта, пункт без метки, число меток не равно
числу пунктов. Регулярки, никакой магии. Это твоя болевая точка, и она
проверяется бесплатно.

**Статус и объём в дереве.** Знаки, время чтения, `draft` / `synced` из
front-matter. Чтобы видеть состояние книги, не открывая каждую главу.

## Чего в этой версии не делаем

Облака и внешние базы данных, бэкапы по расписанию, подключение нейросетей,
голосовой ввод, ветвление версий под разных агентов, права доступа по путям.
Всё это в `plan-studio.md`.

Про права скажу отдельно и честно: галочки в читалке ограничивают только то, что
идёт через её API и задания. Агент с доступом к терминалу читает базу с диска
напрямую, минуя любые настройки. Настоящая изоляция — права файловой системы.
Формат под права я в `agents.json` заложу, но включать не буду: это создаёт
ощущение защиты, которой нет.

## Порядок работы

1. `agents.json` + чтение реестра + совместимость со старым конфигом.
2. Папка `agents/` с адаптером hermes; `hermes_link.py` становится тонкой обёрткой.
3. Автоопределение профилей Hermes + страница «Агенты» с галочками и проверкой связи.
4. Привязка: файлы `.agent.json`, наследование вверх, меню трёх точек в дереве.
5. `--author` в `mark` и `newver`, подстановка из привязки.
6. `sync/yonote.py`, кнопка «отправить в ENOT», страница расхождений.
7. Попутное: поиск, diff в браузере, проверка сносок, статус и объём.
8. `install.sh` / `install.ps1`, README, образцы конфигов.

Пункты 1–5 — ядро, без них мультиагентность не работает. Пункт 6 можно делать
параллельно, он ни от чего не зависит.
