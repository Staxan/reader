# Orchestra: рабочее место для длинных документов

Автор: Ника. Дата: 4 сентября 2026. Версия документа: 1.0

Это второй документ. Первый — `plan-reader.md`, там ближайшая работа по читалке.
Здесь то, что вырастает из неё дальше: отдельный продукт, а не доработка.

## Что это такое

Читалка решает узкую задачу: прочитать главу, оставить замечание, отдать агенту.
Продукт, о котором мы говорим, шире — рабочее место, где документ живёт целиком:
текст, картинки, видео, таблицы, графика, справочные материалы, версии,
замечания, агент-исполнитель и выход в веб, PDF или Word.

Такого сейчас нет. Есть редакторы без агентов (Word, Google Docs), есть базы
знаний без работы с текстом (Notion, Obsidian), есть агенты без интерфейса для
длинного текста. Пустая ниша ровно посередине: **человек редактирует, агент
делает, версии не теряются.**

Название: Orchestra остаётся именем системы, читалка становится её первым
модулем (Reader). Так и в README уже написано.

## Главное решение: в каком формате хранить документ

Ты сказал — HTML, рабочий формат. Здесь я возражу, и это важно возразить сейчас,
а не когда всё будет написано.

HTML прекрасен на выходе и плох на хранении. Три причины:

**Версии перестают читаться.** Наша система замечаний привязывает цитату к блоку
текста через хэш (`structure.py`, `anchor` с `bhash`). В HTML одно нажатие в
редакторе меняет атрибуты половины документа, хэши едут, и все замечания
отваливаются. `diff` между версиями превращается в кашу из тегов вместо текста.

**Файл перестаёт быть текстом.** Сейчас главу можно открыть в блокноте и
прочитать. Это не мелочь: база из 780 файлов переживёт любую программу, включая
нашу.

**Один формат хранения не даёт трёх выходов.** Веб-издание, PDF и Word верстаются
по-разному. Из HTML в Word получается плохой Word.

Правильно так: **хранить структуру, отдавать HTML.** Файл остаётся текстовым, с
front-matter и блоками — как сейчас. Медиа лежит рядом в `_media/`, в тексте
только ссылка. Из этого рендерятся все три выхода: HTML для веб-издания, PDF,
DOCX. Редактор в браузере пишет обратно структуру, а не разметку.

Веб-издание при этом не страдает: `/export` в читалке уже отдаёт готовый кусок
HTML с CSS. Это направление и надо развивать.

## Модули

**Editor.** Правка в браузере с сохранением блочной структуры. Вставка картинок,
видео, таблиц, схем. Не WYSIWYG-редактор общего назначения — только блоки,
которые мы умеем версионировать.

**Materials.** Панель справа, привязанная к проекту и документу: образцы статей,
картинки-референсы, видео, вырезки, ссылки на страницы. Переключаешь документ —
материалы меняются на нужные. Хранится как папка `_materials/` рядом с
документом плюс манифест со ссылками. Твоя идея, и она сильная: сейчас весь этот
материал живёт в чате и теряется.

**Agents.** То, что делаем в читалке: реестр, автоопределение, привязка к
документам и коллекциям, адаптеры под Hermes, Codex, OpenCode, Claude Code.
Отказываться от агентов незачем — это ядро ценности. Мне через читалку дешевле
работать, чем через API: файлы читаются напрямую, текст не пересказывается в чат,
токены не тратятся.

**Search.** Текстовый поиск по базе (уже в читалке) плюс смысловой на локальной
модели.

**Export.** HTML для веб-издания, PDF, DOCX. Сборка всей книги целиком: порядок
глав, сквозная нумерация сносок, единый список источников.

**Storage.** Несколько баз с переключением. Локальные папки, сетевые, папки
облачных клиентов.

**Backup.** Снимок базы по расписанию и обязательный перед созданием версии.

**Plugins.** Расширения на будущее, вплоть до генерации видео. Каркас нужен
сразу, иначе всё врастёт в ядро.

## Облака и базы данных: где я осторожна

Список баз с переключением — легко. Читалка работает с обычными файлами и не
знает, локальные они или сетевые.

Прямая работа с Google Drive по API — сложнее, чем кажется. OAuth, обновление
токенов, свой слой записи. И главная опасность: запись у нас атомарная через
переименование файла, а синхропапка при одновременном доступе плодит
«конфликтные копии». Для базы книги это потеря правок.

Честный путь на первое время: поле «путь к базе» и папка, которую синхронизирует
клиент Диска. Результат тот же, кода ноль. Прямой API — позже, и только для
бэкапов, где запись односторонняя и безопасная.

Про бэкапы: каждые пять минут не нужно. Версии неизменяемы, база сама себе
история. Достаточно снимка раз в сутки плюс обязательного перед созданием новой
версии. Расписание в настройках пусть будет, но по умолчанию — так.

## Дешёвая нейросеть внутри системы

Идея верная: локальная 20B закрывает механику, где не нужен вкус, и не тратит
дорогие токены. Где именно она полезна, по убыванию отдачи:

**Смысловой поиск.** Не по словам, а по мысли: «где я писал про зарплату
робота». На 780 файлах это главная нехватка прямо сейчас.

**Проверка сносок и источников.** Метка `[N]` без пункта, пункт без метки,
издание из запретного списка, ссылка не открывается. Часть проверяется
регулярками, часть — моделью: сверить, что источник действительно про то, о чём
абзац.

**Слежение за ссылками.** Страница жива, изменилась, умерла. Плюс автоматическая
копия в веб-архив: для книги это критично, источники исчезают за год.

**Ссылочная база проекта.** Твоя идея с материалами, доведённая до конца:
страницы привязаны к документу, модель периодически проверяет, что там нового, и
пишет короткую сводку изменений.

**Черновая вычитка.** Опечатки, повторы слов в соседних абзацах, кривое
согласование, канцелярит по списку — «важно отметить», «в рамках», «в контексте».
Не редактура, а сор, убранный до моей работы.

**Карточка документа.** О чём глава в трёх строках, какие цифры и факты, где
пусто. Обновляется при сохранении.

Ещё две вещи, которых ты не называл, а они дорого стоят:

**Поиск противоречий между главами.** В одной главе цифра одна, в другой другая.
Модель сверяет числа и утверждения по всей книге. Для книги с источниками это
защита от позора.

**Черновик замечания по надиктованному.** Ты говоришь сумбурно и длинно, модель
складывает в одну формулировку, ты правишь и сохраняешь.

Оговорка про железо. Локальная модель в виртуальной машине пойдёт только на
процессоре: проброс видеокарты в настольном VMware невозможен, это мы уже
выяснили. Значит либо модель на хосте Win11 с NVIDIA и обращение по сети, либо
медленно. В настройках достаточно поля «адрес модели» — тогда работает и так, и
так, и место запуска можно менять без правки кода.

## Голос

Ты диктуешь. В браузере есть распознавание речи — нажал, сказал, замечание
записано, без переключения на другое приложение. По отдаче для тебя лично это
сильнее половины остального списка.

## Что бы я добавила от себя

**Словарь проекта.** Имена, термины, единые написания, запрещённые слова. И
автоматическая проверка текста по нему. В книге на 20 глав расхождения в
написании неизбежны, а ловить их глазами — мучение.

**Карта фактов.** Все цифры и утверждения с источниками в одной таблице. Видно,
что нечем подтвердить, и что противоречит соседней главе.

**Режим чистого чтения.** Без пометок и цитат — как увидит читатель. Сейчас глава
всегда в рабочем виде, и оценить её как текст невозможно.

**Состояние книги на одном экране.** Главы, объём, статус, открытые замечания,
непроверенные источники. Одна страница вместо обхода дерева.

**Дневник работы.** История уже пишется по документам. Собрать её в одну ленту:
что делалось за неделю, сколько замечаний закрыто. Полезно и для дисциплины, и
для понимания, где книга встала.

## Границы: чего не делать

Не превращать в Notion. Ценность системы — файлы на диске и чистый Python без
зависимостей. Появятся серверная база данных, сборка фронтенда и десяток
библиотек — продукт станет неподъёмным для установки и умрёт от собственного
веса. Всё, что можно оставить файлом, должно остаться файлом.

Не делать универсальный редактор. Мы работаем с длинными структурированными
документами. Попытка заменить Word закончится плохим Word.

Не обещать двусторонний автосинк с чем угодно. Один источник правды, поток в
одну сторону — иначе конфликты съедают всю пользу.

## Лицензия и распространение

MIT — если главное, чтобы люди форкали и дописывали. Но выпущенное под MIT назад
не отзовёшь: любой может собрать закрытый коммерческий продукт из твоего кода.

Если коммерция вообще рассматривается — Apache 2.0 надёжнее (защита от
патентных претензий, требование сохранять уведомления), а платные части держатся
отдельными модулями поверх открытого ядра. Так делают почти все, кто начинал с
открытого кода.

И честно про продукт: он станет продуктом не от лицензии, а когда установится у
человека без WSL, без Hermes и без твоей конкретной машины. Сейчас всё завязано
на неё. Установка из репозитория одной командой — первый шаг в эту сторону, и он
уже в плане читалки.

## Как из читалки вырастает система

1. **Читалка с агентами и ENOT** — `plan-reader.md`. Это фундамент: реестр
   агентов, адаптеры, привязка, синхронизация, установка из репозитория.
2. **Материалы и поиск.** Панель справа, текстовый поиск, локальная модель для
   смыслового поиска и проверки сносок.
3. **Editor и медиа.** Правка в браузере, картинки, таблицы, схемы.
4. **Export.** HTML для веб-издания, PDF, DOCX, сборка книги целиком.
5. **Storage и Backup.** Несколько баз, снимки, облако для бэкапов.
6. **Plugins.** Каркас расширений, всё крупное дальше — плагинами.

Порядок не случайный: каждый шаг полезен сам по себе и не требует следующего.
Если остановиться на любом — то, что сделано, продолжает работать.
